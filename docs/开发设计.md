# 调查 Agent 的工程边界

目标是让求职者在本机完成名单导入、企业调查、岗位核查与反馈。开发顺序见[实施计划](首版实施计划.md)，持久化关系见[数据模型](数据模型.md)。

默认从已登记的城市官方名单取候选。深圳先用可按哈希复核的公示附件。中文企业全称用于发现公开招聘页面，实际页面必须能确认该企业是招聘主体；搜索标题只用来排序。页面可以提供可核实入口，也可以提供一条具体岗位正文。调查分别保存两类证据，供样本汇总和人工核查。

企业发现也可先查产品、项目和技术工作。业务调查复用来源查找、页面快照和次数上限。只有正文能定位企业全称和相关原文时才自动生成企业线索；岗位、工作地点和届别仍由招聘证据判定。用户可把企业名与方向词带到招聘软件继续查找，核查进度保存在本地清单。

关键词反查以城市和业务词搜公开案例，从同一页验证企业全称、业务内容和城市关联。名单比对使用规范化全称，绑定具体的公示快照。同一快照中存在重名时跳过待消歧。项目落地地和企业在当地的业务活动可作为企业线索依据；岗位工作地需由具体招聘原文核对。

## 调查运行

单企业是一次调查的边界，批次固定城市、岗位方向、可选届别、样本和工具次数上限。主体存在歧义时先核实企业与招聘入口的关系。找到岗位后再补职责、地点、应届条件或时效，优先解决影响使用者判断的缺口。任务状态只携带材料 ID、缺口、已执行查询和剩余次数。网页正文按快照保存。

| 环节 | 输入与输出 | 职责 |
| ---|---|---|
| 导入 | 名单 → 来源快照及带页码的条目 | 代码解析保留序号和原名；同名不自动合并，解析不完整可定位 |
| 发现与取页 | 企业、查询或来源 URL → 候选页及正文快照 | 来源适配器区分无结果、访问失败与正文缺失；记录获取时间、链接和内容 hash |
| 语言判断 | 任务和编号片段 → 候选主体、岗位、逐字段判断及缺口 | 本地模型经可替换接口调用，保留模型、提示和规则版本。片段保留标题、否定词、日期与岗位边界 |
| 校验与补查 | 候选判断 → 已验证引用、未知项、下一步 | 代码校验结构、原文位置、实体关联、重复查询和次数上限；语义支持度由样例和人工抽查验证 |
| 核查与反馈 | 调查 ID → 分层结果、原文、反馈 | 保留原始调查与纠错历史；重开界面读取已有结果 |

默认提供随仓库分发的合成材料和固定响应，用于演示与回归。真实调查使用本地模型、无需账户的公开来源发现适配器和可公开读取的招聘页；也可由用户直接提供企业入口。来源适配器须用真实企业全称验证能发现可核查页面，记录候选及取舍。每条真实调查必须标明实际材料覆盖面。固定响应只在回放模式使用。

## 模块与恢复

Python 应用用例负责调查循环，SQLite 负责持久化，名单解析、来源发现、正文读取、模型推理和 UI 在边界接入。CLI 与核查界面调用同一用例。先用普通函数和明确的状态转移实现。后续有跨步恢复或历史材料检索问题时再比较图编排或索引方案。

按企业及调查 ID 保存已完成步骤。搜索、取页和推理分别有次数、超时及文本长度上限，重试计入上限。恢复时复用已保存的步骤与快照，重查另建调查。取页仅访问公开 HTTP(S) 页面，校验每次跳转的目标，排除本机和内网地址；本地模型地址由用户在应用配置中设置。网页文字不能改变工具配置或触发投递、联系等动作。

## 结果如何读

招聘依据、待确认机会、值得关注企业分别展示。若深圳招聘页明确写有“大模型应用开发”，可以展示岗位和岗位地点的引文；如无届别和截止日期，两项都显示未知。企业总部地址、同公司另一社招岗位的经验要求均不能补入这一行。抓取日期与岗位有效性分别保存。
