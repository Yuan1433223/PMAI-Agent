# 数据模型：先保留关系，再实现表

2026年11月23日。当前 SQLite 实现在 `pmai_agent/lists.py`、`investigation.py` 和 `review.py`。名单三表保存文件 hash、原始行和独立主体；调查表保存目标与进度，visits 按调查和 URL 保存单岗位快照，claims 引用同一快照的原文偏移，feedback 追加记录。岗位键按来源 ID 保存于 visits；以下为逻辑设计与后续演进参考。关联：[需求](需求.md)、[开发设计](开发设计.md)。

深圳名单接入增加了 `official_lists`、`entry_positions` 和 `verified_sources`，分别保存官方附件与来源状态、PDF 原始行定位、招聘入口的主体原文及分析所用快照。三张表按需初始化，已有当前版企业与调查 ID 可继续回查。

`saved_leads` 记录每个已保存的企业或岗位的核查进度，`lead_observations` 记录历次调查产生的出处、搜索词和依据。重跑调查保留首次保存时间和用户处理进度，源证据可回查对应调查。岗位身份沿用来源岗位键，官方名单企业沿用各自登记身份。

关键词反查沿用现有调查与快照表。调查配置记录搜索词、名单快照 ID 和比对状态；`claims` 的 `business_place` 保存城市关联原文位置，与招聘岗位的 `city` 判断独立。列表和 CSV 读取这次来源附带的比对结果。

## 一个文件、多张表

计划 `data/app.sqlite3` 保存业务记录。SQLite是数据库引擎，文件中可以有多张关联表。文档里列的实体不是同一张表的不同列。

```text
DocumentSnapshot ──< SourceEntry >── Company ──< Investigation
                                          ├──< JobLead
                                          └──< Claim >── Investigation
JobLead ──< Claim
Company / JobLead ──< Feedback
Claim ── evidence_refs ──> DocumentSnapshot
```

`──<` 表示一对多。Claim的证据可以来自多个快照；图中“Company / JobLead”是反馈目标的两种情况，不是另一张实体表。

| 表（计划名） | 关键字段与含义 |
| --- | --- |
| companies | id、主体名称、消歧状态、已核实别名；名称不直接作为全局唯一身份 |
| document_snapshots | id、类型、出处/URL、获取时间、内容hash、内容位置、解析版本；保留不同获取或解析版本的记录 |
| source_entries | id、document_id、row_no、raw_name、page_no、company_id可空；未消歧时仍保留原始行 |
| investigations | id、company_id、目标/规则/prompt/模型版本、执行状态、查询结果状态、起止时间与预算消耗；重查是新记录 |
| job_leads | id、company_id、首次发现调查、来源定位和原岗位标识；不能只凭标题合并岗位 |
| claims | id、investigation_id、company_id、job_lead_id可空、字段、值、支持/反驳/未知、判断类型、evidence_refs、原因 |
| feedback | id、企业或岗位目标、实验ID、记录时间、原已知/新增、是否值得继续了解、用户纠错及依据 |

第一版证据引用可用受校验的JSON数组保存document_id、片段与位置；引用校验由代码执行，不伪装成SQLite已提供所有关系约束。需要复杂多对多查询时再拆claim_evidence表。

## 关键约束

- `source_entries` 的 `(document_id, row_no)` 唯一；重复导入可查到同一原始行。新文档版本不能无条件覆盖旧行。
- 外键约束在连接时显式启用。Claim所属调查、企业、岗位必须相容，跨表语义由服务层校验。
- 地点、应届条件、职责分别存判断与依据，且关联同一JobLead；禁止把甲岗位的深圳地点与乙岗位的应届要求拼成一个结论。
- 抓取时间、页面公布时间与岗位有效性分别表达；未知为未知，不自动填当前日期。
- Company是企业身份，Investigation是一次带目标的运行，Claim是可修正判断；三者不能合成“一家公司最新的一行结果”而丢掉过程与版本。
- 程序内部执行状态、查询访问结果和业务判断分别维护。失败或无结果不写成“不招聘”。

## 首个切片，只做名单进入

先建document_snapshots、source_entries、companies；解析结果以序号、原名、页码落库。公司暂未消歧时可以不分配company_id，不靠名称直接猜合并。数据库先保存入口事实，不调用模型也能检验完整性和重复导入行为。

进入真实企业调查后再建investigations、job_leads、claims；开展作者实验时再建feedback。不为架构图一次生成全部空表。

数据库迁移与验证办法在实现时确定：第一批至少检查连续序号、重复导入、同名未合并、来源可定位，以及解析失败不静默丢行。

## RAG与数据增长

公司记录多少条不是RAG开关。需要对历史页面做反复语义检索、当前检索存在可观察不足，并能用固定问题与支持材料验证收益时，再比较关键词、全文、向量及混合检索。LlamaIndex是可选实现工具，SQLite可继续承担业务存储，不能把引入框架当作迁移数据库。
